# P0: воспроизводимая диагностика

## Последовательный запуск сравнения моделей

Из корня репозитория запустите новую серию (каталог результата должен ещё не существовать):

```sh
python3 backend/evaluation/run-model-comparison.py --out backend/bin/evaluation-artifacts/my-comparison
```

По умолчанию запускаются Qwen, MiniCPM, Gemma 4 и Jamba с reasoning для local и oracle.
Для выбора моделей используйте `--models qwen2b minicpm5-1b`, для одного набора —
`--kinds local`. Gemma 3 и Phi доступны как `gemma3-4b` и `phi4-mini`, без native
переключения reasoning. `--langfuse` дополнительно импортирует сырые результаты;
оценки правильности не выставляются, readback не выполняется. Полный список — `--help`.

Скрипту нужны `llama`, собранный `backend/bin/prompt-eval`, сохранённые веса и
артефакты baseline. Проверяются SHA256 весов, а параметры и hashes входов сохраняются
в `configuration.json`. Результаты, включая ошибки, находятся в `runs/`, ход работ —
в `status.json`, логи и preflight — рядом. Сгенерированные ответы требуют отдельной
проверки по источнику; профили разных моделей различаются sampling. Остановка Ctrl+C
сохраняет частичные данные; автоматического возобновления нет.

Команды запускаются из корня backend. `retrieval-eval` по умолчанию выполняет
только поиск; `prompt-eval` — локальную генерацию с `default,strict-ru`.
OpenCode, удалённая модель и фиксированное число вопросов не нужны.

```sh
# Нужен только embedding-сервер. LLM не загружается и не вызывается.
go run ./cmd/retrieval-eval --embedding-url http://127.0.0.1:18082 \
  --modes vector,hybrid --out bin/evaluation-artifacts/my-run/retrieval

# Тот же pipeline с локальным генератором, включая штатный retry 256 -> 512.
go run ./cmd/prompt-eval --embedding-url http://127.0.0.1:18082 \
  --llama-url http://127.0.0.1:18081 --model assistance-2b \
  --out bin/evaluation-artifacts/my-run/2b-local

# Вручную проверенные исходные фрагменты, обход embeddings и поиска.
go run ./cmd/prompt-eval --kind oracle \
  --embedding-url http://127.0.0.1:18082 \
  --llama-url http://127.0.0.1:18081 --model assistance-2b \
  --out bin/evaluation-artifacts/my-run/2b-oracle
```

Параметры `--cases`, `--corpus`, `--game`, `--model`, `--profiles`, `--modes`,
`--seed`, `--limit`, `--embedding-model`, `--embedding-revision`, `--dimensions`
задают эксперимент явно. У `retrieval-eval` также есть `--kind local|oracle`.
Не переиспользуйте каталог вывода для другой конфигурации.

Локальные llama.cpp-серверы должны предоставлять `/props` с `model_path`,
`model_ftype`, `build_info`, настройками runtime, а генератор — ещё и шаблоном чата.
Evaluator хеширует фактический GGUF по пути сервера; нужен доступ к этому файлу.
Шаблон должен поддерживать `enable_thinking`: evaluator проверяет наличие этого
параметра и отправляет `false`. Это проверка интерфейса, а не универсальное
доказательство отсутствия reasoning; поддержку конкретной сборки проверяйте в
логах и ответах. Для native instruct-моделей без этого параметра предусмотрен
`--verified-non-thinking`: сначала отдельно проверьте `/apply-template` и ответ
сервера без reasoning. Флаг также допустим при проверенном server reasoning budget
0; это отдельное ограничение режима, а не native non-thinking модели. Флаг
сохраняется как `generation_runtime.non_thinking_verified`, фактический шаблон
и `/props` продолжают записываться без подмены.
Для моделей с обязательным reasoning есть отдельный `--allow-reasoning`:
он сохраняет `generation_runtime.reasoning_allowed=true` и не выдаёт этот режим
за проверенный non-thinking. Это не меняет запрошенный `enable_thinking=false`:
шаблон такой модели может его игнорировать. Reasoning расходует тот же лимит
256/512 токенов. Эти два флага взаимоисключающие. Сравнение такого режима нужно
помечать отдельно от моделей с отключённым thinking.
`--enable-thinking` действительно отправляет `enable_thinking=true`; одного
`--allow-reasoning` для переключения управляемого шаблона недостаточно.
Бюджеты задаются `--max-tokens` и `--retry-max-tokens` (по умолчанию 256/512),
sampling temperature — `--temperature` (по умолчанию 0.2). Фактические значения
сохраняются в manifest и payload. Большие бюджеты должны помещаться вместе с
prompt в окне сервера. Это параметры evaluator, штатные настройки сервиса
по умолчанию остаются прежними.
Для контрольной 4B запускайте ту же команду с отдельным сервером,
`--model` и каталогом вывода. Настройки других samplers и размер окна берутся из
`/props` и входят в manifest; их нужно держать одинаковыми при сравнении моделей.

`manifest.json` фиксирует SHA256 корпуса, вопросов, всех Go-файлов и зависимостей,
Git HEAD, точные веса, тип квантования, версию llama.cpp, шаблон чата, runtime и
параметры генерации. Корпус копируется в `corpus/<game>.rag`, исходник не меняется.
Запускайте на закрытом, неизменяемом SQLite-файле без активного WAL/writer.
Кеш ключуется точным embedding-входом и профилем (GGUF hash, alias/revision,
размерность, формат входа); отдельный cache-manifest фиксирует реальные векторы.
Префиксы не добавляются: P0 измеряет существующий raw-text путь.
Успешные ячейки возобновляются только при совпадении manifest и кеша; ошибочные
перезапускаются. Запись JSON атомарная. Ошибка отдельной генерации сохраняется,
остальные случаи продолжаются, команда завершается ненулевым кодом.

## Эталоны и trace

`dino-crisis-fts/questions.json` содержит существующие 20 вопросов. Для новых
наборов достаточно непустого JSON-массива с уникальными безопасными `id`,
`question`, `expected` и списком `evidence`:

```json
[{"id":"code","question":"Какой код?","expected":"0392",
  "evidence":[{"document_id":1,"sequence":28,"text_sha256":"SHA256 точного текста фрагмента"}]}]
```

Хеш защищает от незаметной смены chunking; при пересборке корпуса эталон нужно
сверить заново с источником. Старое `relevant_sequences` поддерживается для
регрессий одного документа, но для oracle нужны проверенные `evidence`.
Пустые evidence означают неответимый пример: oracle его пропускает. Oracle без
единого подтверждённого фрагмента завершается ошибкой. Для составного вопроса
все указанные доказательства считаются необходимыми. Альтернативные допустимые
наборы пока не моделируются. Это диагностический набор одной игры, не закрытый
benchmark нескольких игр из последующих этапов плана.

Каждая запись содержит кандидатов до отбора, кандидатный пул после ранжирования,
выбранные доказательства с ID/текстом, отдельные cosine, BM25 и RRF. BM25 меньше —
лучше, RRF больше — лучше; отсутствующий сигнал не заменяется нулём. `rerank`
отсутствует, потому что реранкер в P0 не запускается. Пул dense ограничен
`max(20, 4*limit)`, hybrid — объединением двух таких пулов. Вопросы о начале
игры проходят через общее ранжирование: принудительный выбор первых фрагментов
первого документа удалён после P0. Сохранённый baseline P0 отражает прежний алгоритм.

Trace включает время embedding-запроса, поиска, сборки контекста, генерации,
всего запроса и каждого completion/retry; payload, finish_reason и реальные
`prompt_tokens`/`completion_tokens`, если сервер прислал usage. Новые traces
сохраняют контент каждой попытки, включая усечённую, и отдельный
`reasoning_content`, когда сервер его вернул. `reasoning_tokens` записывается
только при наличии в usage, без оценки по длине строки. Итоговый ответ берётся
из content; рассуждение в него не подставляется. Исторические артефакты новых
полей не содержат. Ошибки сохраняют контекст и причину сбоя.
`source_present=false` и `parsed_present=false` в эталоне
позволяют вручную отметить отсутствие факта в исходнике либо потерю при разборе.
Без этих проверок evaluator не угадывает причину upstream-ошибки.

`summary.json` отделяет полноту кандидатов от полноты контекста. Верный retrieval
не означает верный ответ. После oracle/local прогонов проверяйте ответ вручную
по `expected`, исходнику и полному набору evidence, отмечая неподтверждённые
добавления и спойлеры. `generation_review_required` означает необходимость этой
проверки. Уточнение вместо ответа на ответимый вопрос — нерешённый случай.

## Проведение сравнения в OpenCode

Для локального управляющего агента с окном 150 000 токенов используй
[стартовый промпт](../../opencode-prompts/MODEL-COMPARISON-PROMPT.md). Условия сравнения вынесены
в [спецификацию](../../opencode-prompts/MODEL-COMPARISON-SPEC.md), сохранение состояния и ограничения
чтения — в [протокол контекста](../../opencode-prompts/MODEL-COMPARISON-CONTEXT.md).
[Шаблоны задач](../../opencode-prompts/MODEL-COMPARISON-AGENT-TASKS.md) подходят и для последовательной
работы без сабагентов. После смены сессии используй
[промпт продолжения](../../opencode-prompts/MODEL-COMPARISON-RESUME.md) с конкретным каталогом серии.
Эти инструкции не возобновляют остановленные прогоны автоматически.

## Артефакты и границы измерений

Небольшие эталоны и текущий baseline (`baselines`) хранятся в Git.
Отчёты и каталоги сравнений исключены из Git. Новые эксперименты запускайте
через `langfuse/pipeline.py run`: результаты загружаются и проверяются в Langfuse. Полные результаты, SQLite, кеш и runtime-логи находятся в
игнорируемом `bin/evaluation-artifacts/` или `tmp/`; сводка baseline указывает
версию, путь и SHA256 архива. Исторические 4B-отчёты не являются текущим baseline.

Тайминги с кешированными embeddings не являются production latency. Первый
вызов модели может быть холодным, последующие — прогретыми; эти режимы нельзя
усреднять как характеристики Steam Deck. P0 на macOS не подтверждает RAM,
энергопотребление, TTFT или влияние на frame time Deck; эти замеры остаются
аппаратной проверкой на целевом устройстве. Здесь измеряется полное время
нестримингового completion, а не TTFT. Один seed — диагностический срез.

Очистка перед P0 убрала экспериментальные изменения chunking/структуры,
семантический detector начала, OpenCode, изменения CLI/API и дедупликацию
цитирований. Hybrid-поиск, профили промптов и их тесты оставлены как основа
сравнения. Веса, корпуса и прежние результаты не удалялись; резервная копия
предыдущего рабочего дерева лежит рядом с проектом.
