# Контекст и восстановление в OpenCode

Этот протокол задаёт способ выполнения. [Спецификация](MODEL-COMPARISON-SPEC.md) задаёт условия эксперимента. Ограничение контекста не разрешает сокращать тестовый набор, менять sampling, рубрику или пропускать review. При нехватке окна дели работу на задачи и сохраняй состояние.

## Бюджет управляющего агента

Окно 150 000 токенов включает системные инструкции, историю, задания, вывод инструментов и место для следующего ответа/reasoning. Реальный доступный объём зависит от модели и сервера. Проверь лимит входа и выхода в профиле OpenCode и у провайдера; надпись в промпте не меняет эти ограничения. Если фактический предел меньше, уменьши пороги с тем же запасом.

Рабочие ориентиры, а не измеренные свойства модели:

| Что ограничиваем | Предел или действие |
|---|---|
| Общий входной контекст | Стремись оставаться ниже 90 000 токенов |
| 90 000 | Сохрани checkpoint; подготовь освобождение контекста |
| 100 000 | Не начинай следующую задачу; compaction или новая сессия |
| Резерв относительно окна 150 000 | Не менее 50 000 на следующий вывод, ответ и служебные операции |
| Один review-пакет | До 3–5 случаев и около 20 000 входных токенов вместе с инструкциями |
| Один вывод инструмента | До 12 KiB; большие данные извлекай выборочно |
| Возврат сабагента | До 300 токенов, только сводка и пути |
| HANDOFF | До 1 000 токенов |

Пользуйся счётчиком OpenCode/реальным tokenizer выбранной модели, если он доступен. Не выдавай оценку по символам за точный токеновый счётчик. Без счётчика ограничь содержимое review-пакета 48 KiB UTF-8, используй максимум 3 случая и начинай свежую сессию/compaction после пяти ограниченных задач или раньше при больших чтениях. Это консервативные эвристики, а не эквивалент токенов. Не откладывай checkpoint ради заполнения окна.

## Чтение и вывод инструментов

- Ищи через `rg`, ограничивая каталог и исключая `backend/tmp/`. Начинай с имён/схем и нужных функций, затем читай соответствующий участок.
- Не делай `cat` больших results.json, JSONL, embedding cache и логов. Скриптом выбери case_id, поля или небольшой диапазон и заранее проверь размер вывода. Ограничение числа строк не защищает от одной огромной JSON-строки.
- Команды генерации и экспорта направляй в файлы. В чат выводи exit status, счётчики и короткую сводку ошибок. Не печатай секреты.
- Полный конечный ответ и необходимые source spans должны быть прочитаны reviewer. Если не помещаются, уменьши число случаев, читай по частям с сохранением заметок; если даже один случай превышает доступный бюджет, зафиксируй blocker. Не выставляй оценку по обрезанному тексту.
- Ограничения касаются передачи в чат. Исходные артефакты сохраняются полностью; не урезай их ради экономии контекста.

## Состояние на диске

В новом каталоге серии создай `_control/`. Не создавай его в остановленных или baseline-сериях. Это служебные файлы конкретного запуска, а не новая инфраструктура проекта.

`state.json` — небольшая текущая сводка, обновляемая через временный файл и atomic rename. Минимальные поля:

```json
{
  "schema_version": 1,
  "experiment_id": "<new-series-id>",
  "status": "running",
  "phase": "prepare",
  "protocol_path": "<path>",
  "protocol_sha256": null,
  "rubric_path": "<path>",
  "rubric_sha256": null,
  "queue_path": "<path>",
  "current_job_id": null,
  "next_action": "<one-specific-action>",
  "counts": {"planned": 0, "generated": 0, "reviewed": 0, "published_verified": 0},
  "active_processes_path": "<path>",
  "updated_at": "<ISO-8601>"
}
```

До заморозки протокола hash может быть `null`; после неё запиши вычисленное значение. Очередь содержит стабильные job_id, тип задачи, входы, выходы и статус. Различай `planned`, `running`, `generated`, `reviewed`, `audited`, `published_verified`, `failed`, `needs_split`. Статус всей серии: `running`, `awaiting_context`, `stopped_user`, `done`. Процесс завершился — не значит, что серия завершена. Достижение стадии генерации не означает прохождение тестов.

Очередь следует этапам: подготовка → генерация → review → аудит/разрешение расхождений → публикация и readback → отчёт/архив. Внутри этапа бери одну задачу. Для review/audit храни статусы отдельных пакетов; для каждого model/kind отдельно отмечай генерацию, проверку и публикацию. Счётчики в state — сводка очереди с явно определённой единицей, не ручная оценка прогресса. Подготовку evaluator ограничивай одной проверкой или правкой за задачу; при необходимости читай целевую функцию и соответствующий тест, а не весь backend.

Дополнительно сохраняй:

- `HANDOFF.md`: цель, ссылки на неизменяемые условия, последний проверенный результат, один следующий шаг, блокеры и работающие процессы. Без полных ответов и истории рассуждений.
- `jobs.jsonl`: журнал переходов со временем, job_id, путями и hashes. Не загружай журнал целиком; читай нужную запись.
- Реестр собственных процессов: PID/PGID, время старта, команда, порты, job_id и состояние. При восстановлении сверяй живой процесс с этими признаками; PID мог быть переиспользован.
- Реестр публикаций: job_id, уникальный префикс, Langfuse IDs, отправленные и прочитанные обратно scores. Сохраняй после каждой подтверждённой операции.

Не дублируй ответы и большие manifests в state/HANDOFF. Числа и hashes получай кодом. Если произошёл сбой между записью результата и checkpoint, сначала проверь существующий результат и восстанови статус; не перегенерируй автоматически.

## Смена контекста

1. Сохрани завершённые артефакты и обнови state/HANDOFF, включая активную команду и точный следующий шаг.
2. Используй доступный механизм compaction OpenCode или свежую сессию. Не рассчитывай на сохранение точных hashes и оценок в автоматическом резюме.
3. В новом контексте прочитай AGENTS.md, state, HANDOFF и только относящиеся к следующему шагу параметры. Проверь hashes замороженных условий, текущий результат и активные процессы.
4. Продолжи одну задачу. Работающий CLI наблюдай по файлам/статусу, не запускай заново. Если процесс завершился, проверь артефакты перед изменением статуса.

Compaction заменяет историю резюме с потерей деталей; сабагенты OpenCode могут получать свежий контекст. Это возможности среды, а не замена checkpoint: [compaction](https://opencode.ai/docs/compaction/), [agents](https://opencode.ai/docs/agents/).

При наличии настройки compaction оператор может заранее выбрать больший резерв. Для проверенной локально версии OpenCode **v2.2.5** пример отдельного фрагмента конфигурации:

```json
{
  "compaction": {
    "auto": true,
    "keep": {"tokens": 15000},
    "buffer": 50000
  }
}
```

При корректно заданном окне 150 000 такой резерв означает начало автоматической compaction примерно у 100 000. Этот пример не был применён к настройкам; не заменяй им существующий конфиг. Для другой версии проверь поддерживаемые поля. Порог зависит от того, какой лимит среды реально знает OpenCode. Автоматическое резюме всё равно не гарантирует завершение эксперимента без checkpoints.

Если агент не может сам открыть свежую сессию/выполнить compaction, сохрани `awaiting_context` и выдай [промпт продолжения](MODEL-COMPARISON-RESUME.md) с конкретным путём. Это запрос технической передачи контекста, а не утверждение о завершении. Не оставляй пользователю собирать состояние по старому чату.

Команда пользователя остановить имеет приоритет: останови только собственные процессы с проверкой принадлежности, сохрани `stopped_user`. Ни compaction, ни промпт продолжения не отменяют остановку без явного нового указания пользователя.
