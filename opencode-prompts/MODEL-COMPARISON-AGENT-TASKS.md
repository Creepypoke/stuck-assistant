# Ограниченные задачи для OpenCode

Эти шаблоны применяются после явного запуска новой серии. Они подходят для последовательного выполнения основным агентом или сабагентом со свежим контекстом. Сабагенты необязательны; их цель здесь — ограничить накопление контекста. Не требуется одновременно работающая команда.

Координатор заполняет `<...>` фактическими значениями. Каждая задача получает только нужные параметры `protocol.json`, входы и ожидаемый выход. Не передавай историю чата. Общая файловая система не обеспечивает изоляцию прав: назначенные пути — рабочий контракт.

## Общая часть каждого задания

```text
Соблюдай AGENTS.md; не сканируй, не читай и не используй backend/tmp/.
Выполни только job_id=<job_id>. Не создавай вложенных сабагентов.
Не меняй protocol.json, рубрику, evaluator и исходные результаты.
Пиши только в <allowed_output_paths>. Сначала проверь существующий результат
и активные процессы: не повторяй уже выполненную или запущенную работу.

Полные данные и логи сохраняй в файлы. Ограничивай вывод инструментов;
следуй MODEL-COMPARISON-CONTEXT.md. При невозможности закончить задачу
сохрани частичный результат и точный следующий шаг, не объявляй успех.

Верни до 300 токенов: job_id, status, output_paths, sha256,
completed_count, error_count, blocker, next_step. Не включай полные ответы,
reasoning или весь прочитанный контекст. Координатор проверит файлы сам.
```

## Runner: проверка и запуск скрипта серии

```text
Серия <series_dir>, ещё не существующий выход <series_dir>/generation.
Протокол: <protocol_path>. Команда: <approved_script_command>.
Реестр процессов: <registry_path>. Лог запуска: <series_dir>/runner.log.

Проверь hashes входов, свободные порты и отсутствие другого процесса серии.
Сверь параметры run-model-comparison.py с замороженным протоколом. Запусти
команду один раз, зарегистрируй PID, время старта и дочерние процессы.
Скрипт сам выполняет preflight, запускает модели и сохраняет логи/results.
Проверь probes: включённый флаг сам по себе не доказывает reasoning.

Сверь generation/status.json, manifests, ожидаемые case_id и hashes;
ошибки отдельных случаев остаются в данных. Не меняй budgets/sampling после
неудачного ответа, не оценивай правильность и не публикуй scores.
При передаче контекста укажи живой процесс; не запускай копию. Скрипт не
возобновляет частичный output. При остановке проверь завершение всех своих
дочерних процессов и серверов; не затрагивай чужие процессы.
```

## Reviewer: до 3–5 случаев

```text
Входы: <packet_path>, <rubric_path>, <source_spans_paths>.
Выход: <review_output_path>. Пакет обезличен: без модели, старых оценок
и reasoning. Не ищи скрытые сведения в соседних файлах.

Проверь каждый конечный ответ полностью по источнику. Проверь факты,
эпизод/условия, порядок и повторы, неподтверждённые добавления, спойлеры,
коды, язык, source-exact названия и runtime по зафиксированной рубрике.
Правильный код не оправдывает ложное объяснение; пустой/обрезанный ответ
и уточнение вместо ответа на ответимый вопрос — провал.

Сохрани JSON по каждому case_id: binding hashes, оценки, конкретную
причину, source-цитату или span и отметку неоднозначности. Не меняй expected
или rubric. Если исходный текст противоречив, сохрани source_issue.
Если пакет слишком велик, верни needs_split с непросмотренными case_id;
не оценивай непрочитанное и не сокращай ответ до удобного фрагмента.
```

## Auditor: новый контекст без первичного review

Используй задание reviewer с отдельным выходным файлом. Передавай исходный обезличенный пакет и рубрику, без оценок/обоснований первого reviewer. Процедуру выборки зафиксируй до генерации: например, все провалы и пограничные случаи плюс 20% успешных с фиксированным seed. Причину включения случая auditor не получает.

При последовательном выполнении в том же контексте, где уже видны первые оценки, это повторная проверка, а не слепой аудит. Сохрани данное ограничение в отчёте. Даже свежий AI-сабагент не является независимым человеческим судьёй.

## Координатор: один проверяемый переход состояния

- Держи в контексте state, HANDOFF, текущую задачу и нужный раздел спецификации.
- Проверяй файл результата, его bindings, полноту и hash перед принятием.
- Объединяй данные скриптом; не копируй сотни записей через чат.
- Расхождения оценок разрешай по источнику с сохранением истории.
- Импортируй реальные outputs и проверенные scores через существующий exporter; проверяй readback. Не повторяй публикацию после смены контекста без проверки уже созданных объектов.
- Обновляй checkpoint после каждого пакета. Следующему контексту передавай один конкретный шаг.
- При остановке прекращай выдачу задач и проверяй завершение собственных subprocesses; прерывание сабагента само по себе этого не гарантирует.
