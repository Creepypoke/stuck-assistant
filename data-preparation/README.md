# data-preparation

Самостоятельный Go-модуль для подготовки локальных `.txt`, `.htm`, `.html`
прохождений и создания SQLite `.rag`. Backend получает готовую базу и отвечает
за retrieval и ответы. Python и внешний HTML parser не требуются.

## Сборка и CLI

Требуется Go 1.25+.

```sh
cd data-preparation
make build
cp cli.example.yaml data-preparation.yaml
./bin/data-preparation --config data-preparation.yaml --walkthrough walkthroughs/resident-evil-3-remake.yaml prepare
./bin/data-preparation --config data-preparation.yaml --walkthrough walkthroughs/resident-evil-3-remake.yaml validate
./bin/data-preparation --config data-preparation.yaml --walkthrough walkthroughs/resident-evil-3-remake.yaml build
```

`run` последовательно выполняет `prepare` и `build`. Для AI-режима с обязательным
ревью используйте отдельные команды. Настройки разделены между двумя YAML-файлами:

- `--config` — общий конфиг CLI: именованные профили AI-провайдеров, URL,
  модели, ссылки на переменные с API-ключами, таймауты и размерности embeddings.
  По умолчанию используется `data-preparation.yaml` в текущем каталоге.
- `--walkthrough` — обязательный конфиг конкретного прохождения: игра, входной
  файл, пути артефактов и `.rag`, выбор профилей по именам, лимиты обработки
  и политика ревью. Пример — `walkthroughs/resident-evil-3-remake.yaml`.

Один общий CLI-конфиг используется с любым количеством конфигов прохождений.
Относительные `input`, `artifacts`, `output` разрешаются от каталога файла
прохождения независимо от расположения CLI-конфига и рабочего каталога.
Профили провайдеров определяются только в общем конфиге. Неизвестные поля и
ссылки на отсутствующие профили отклоняются. Объединённый старый формат больше
не принимается: перенесите `providers` в общий файл, остальные поля — в файл
прохождения.
Имеющиеся каталоги артефактов и выходные базы не заменяются: для новой версии
задайте новые `artifacts` и `output`.

## Подготовка

1. Чтение локального файла с ограничением размера. TXT — UTF-8, HTML-декодирование
   учитывает charset. HTML разбирается DOM-парсером: выбираются reader content,
   article, main или body; исключаются навигация, скрипты, реклама в aside,
   скрытые элементы. Произвольная вёрстка может требовать проверки очистки.
2. Извлекаются заголовки, абзацы, пункты списков, строки таблиц и подписи.
   Сохраняются иерархия заголовков, порядок, стабильные ID, Unicode-диапазоны.
   Изображения отмечаются для ревью; OCR и решения с картинок не извлекаются.
3. Без `annotation_provider` создаётся исходная структурная разметка:
   одна карточка на блок с унаследованными заголовками (`source_only`). Это
   воспроизводимый базовый режим, без семантического определения глав/задач.
4. С `annotation_provider` модель группирует соседние блоки в ситуации,
   выделяет этап, ветку, локацию, задачу, условия, предметы, факты, точные коды,
   порядок действий, результат и алиасы. Вход ограничен иерархией раздела и
   `max_batch_chars`; большой неделимый блок вызывает ошибку вместо обрезания.
   Лимит символов не является гарантией длины в токенах: выбирайте его под модель.
5. Цитаты и диапазоны вычисляет приложение. Каждый блок должен быть покрыт
   ровно один раз в исходном порядке. Коды и действия проверяются как точные
   фразы источника. Поля не могут добавлять новые факты.
6. Формируются два представления: контекст с названиями/алиасами для поиска
   и точные исходные доказательства для ответа. Исходник сохраняется полностью.

AI-карточки получают `needs_review`. По умолчанию `require_review: true`
блокирует их сборку. Изучите условия/эпизод/цитаты в `cards.yaml`, исправьте
ошибки и выставьте `validation_status: reviewed` у каждой проверенной карточки.
Это отметка человека, не автоматическая оценка истины. Проверка цитат не
доказывает правильность привязки к игровому этапу.

Для диагностического прогона можно явно задать `require_review: false`.
Это не превращает AI-разметку в проверенную. Статус `source_only` предназначен
для структурного режима, не для обхода ревью AI-карточек.

## Артефакты

| Файл | Содержание |
|---|---|
| `source.bin` | Неизменённые байты входного файла |
| `document.txt` | Нормализованный извлечённый текст |
| `manifest.yaml` | Хеши, версия пайплайна, игра, модель разметки, предупреждения |
| `blocks.yaml` | Блоки, заголовки и диапазоны в document.txt |
| `cards.yaml` | Карточки, факты, условия, точные коды/действия, source spans, ревью |
| `search.yaml` | Предварительный просмотр поискового и ответного представлений |

Редактируйте карточки, а не производный `search.yaml`: при сборке поисковые
представления заново вычисляются из карточек. Изменённые или неполные source
spans отклоняются. При изменении разбиения создайте новую версию артефактов;
одного редактирования block_ids недостаточно — доказательства должны совпадать.

## AI API

`providers` в общем CLI-конфиге — именованные профили. `annotation_provider`
и `embedding_provider` в файле прохождения выбирают их независимо. Поддержаны:

- `type: openai`: API `/chat/completions` для разметки и `/embeddings` для векторов
  (локальный llama.cpp, Ollama с совместимым API, OpenAI-compatible сервисы);
- `type: anthropic`: Messages API `/messages` для разметки.

`base_url` включает API-префикс, например `http://localhost:8081/v1`.
Ключ задаётся именем переменной окружения `api_key_env`; секреты не записываются
в YAML артефактов. Настраиваются модель, timeout, max_output_tokens; для embeddings
также dimensions и version. HTTP перенаправления запрещены, HTTP-ошибки не
выводят тело ответа, которое может содержать данные или секреты.

Совместимость конкретного сервиса с параметрами Chat Completions нужно проверить.
Другие протоколы требуют отдельного адаптера. Без доступной модели разметки можно
подготовить структурный вариант; без реального embedding API сборка `.rag` не
подменяет векторы случайными значениями.

## Контракт .rag и backend

Используется существующая схема SQLite v1: metadata, documents, chunks,
embeddings, FTS5 и триггеры. В metadata чанка помещается `situation-v1`, который
уже читает backend: situation_id, answer_text, source_spans. Поиск использует
расширенный текст, а генерация получает цитаты исходника. Каждая цитата проверяется
по хешу нормализованного документа и диапазону Unicode-кодовых точек [start,end).

Проверенные факты могут формировать компактный answer_text: цитаты фактов, условия,
необходимые предметы, код, результат и нумерованные действия с сохранением повторов.
Если проверенных фактов нет, используется полный исходный текст ситуации. Полная
карточка также сохраняется в metadata чанка.

Векторы записываются float32 little-endian. Количество, размерность, индексы,
конечность и ненулевая норма ответов API проверяются. Сначала строится временная
база, проверяется SQLite integrity_check, затем целый файл публикуется без замены
существующего. Выход не зависит от исходного каталога артефактов.

Embedding-профиль этой версии — `raw-search-text-v1`: без автоматически добавленных
task/query/document prefixes, совместимо с текущим query embedding backend.
Используйте одну модель, revision/version и размерность с обеих сторон. Смена
формата требует согласованного изменения query-пути и пересборки индекса.

Установить готовую базу можно копированием в настроенный storage-dir backend:

```sh
cp output/resident-evil-3-remake.rag ../backend/bin/data/games/
```

Это ручной шаг после проверки качества. `prepare`, `build` и `run` не меняют
каталог действующего backend. Для ответов нужны runtime embedding/LLM-серверы,
но модели разметки больше не нужны.

## Проверки

```sh
make test
make vet
```

Тесты покрывают реальный HTTP-контракт с тестовым сервером, оба протокола разметки,
ревью, потерю/подмену доказательств, числа с ведущими нулями, повторы, порядок
embedding-ответов, SQLite/FTS и защиту от перезаписи. В backend отдельный
интеграционный тест проверяет чтение базы, созданной новым pipeline.

Это проверки реализации, не измерение качества AI-моделей. Оценку retrieval и
ответов выполняйте существующим evaluator backend на новом corpus и отдельном out.
